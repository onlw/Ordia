# Ordia 决策记录（Decision Log）

> 本文件记录已经拍板的关键决策。任何人（包括 AI Agent）想推翻其中一条，必须先在这里新增一条 `Superseded` 记录并说明理由，经维护者确认后才能改变实现方向。
>
> 格式：`D-编号 | 决策 | 理由 | 日期 | 状态`

## 产品与范围

| 编号 | 决策 | 理由 | 日期 | 状态 |
|---|---|---|---|---|
| D-001 | 首要目标用户：**个人用户与专业人士**（学生、白领、自由职业者），先做 C 端口碑，再向团队和企业版扩展 | 体验和颜值是最能拉开差距的地方，也不需要先建企业级能力 | 2026-11-14 | Accepted |
| D-002 | 开发资源：**1–2 人 + 大量 AI 编码**，长期投入 | 决定了必须"单点突破、分阶段扩展"，而不是三件套同时铺开 | 2026-11-14 | Accepted |
| D-003 | 第一个组件：**表格**（对标 Excel） | 性能差异最容易被用户感知；网格渲染（矩形 + 线 + 单行文本）正好是 GPUI 的强项，避开了矢量绘图和复杂排版两个短板 | 2026-11-14 | Accepted |
| D-004 | 表格计算引擎和 xlsx 读写：**以 IronCalc 为起点**（Apache-2.0/MIT），封装在 `ordia-sheet-engine` 接口后面；遇到瓶颈再逐步替换或回馈上游 | 一个人自研公式引擎不现实；接口隔离保证以后可以替换 | 2026-11-14 | Accepted |
| D-005 | 文件格式：**xlsx 作为默认保存格式**；不支持的内容（透视表、宏、复杂图表等）**原样保留、保存时写回**（"不认识也不破坏"）；另外在内部做崩溃恢复和历史版本 | 个人用户的文件大多来自别人的 Excel 或 WPS，保存后丢内容是致命问题 | 2026-11-14 | Accepted |
| D-006 | 平台：**第一阶段只做 macOS + Windows**（以 macOS 为主力开发平台，Windows 每周验证）；Linux 能编译即可，不承诺支持；Web 和移动端放到远期 | 集中精力 | 2026-11-14 | Accepted |
| D-007 | 开源：**核心客户端开源，协议为 Apache-2.0**（与 GPUI、GPUI Kit、IronCalc 一致），个人免费 | 积累口碑、吸引贡献者；协议和依赖保持一致，避免冲突 | 2026-11-14 | Accepted |
| D-008 | **只做单机版**，不做云服务和协同 | 缩小范围。编辑仍然统一用"操作（Operation）"来表达，因为撤销重做、崩溃恢复、历史版本本来就需要它；这样以后如果要做协同，也不用推倒重来 | 2026-11-14 | Accepted |
| D-009 | **前 1–2 年不商业化**：接受 GitHub Sponsors 和捐赠；付费功能（如 AI）等有了用户基础再定 | 和 D-008 一致 | 2026-11-14 | Accepted |
| D-010 | 表格 1.0 功能范围：核心底座 + 条件格式 + 数据验证 + 常用图表 + 打印和 PDF 导出 + 百万行 CSV 导入导出；**数据透视表放到 1.x**（见 D-017）；其他功能尽力兼容 Excel 和 WPS 的已知能力 | 用户选定；透视表按 D-017 分级处理 | 2026-11-14 | Accepted |
| D-011 | 界面风格：**现代简洁**——精简的单行工具栏 + 命令面板（Cmd/Ctrl+K）+ 右侧上下文属性面板；质感参考 Linear、Notion、Numbers、Zed；支持亮色和暗色主题 | 高颜值是核心诉求 | 2026-11-14 | Accepted |
| D-012 | 性能：**不设绝对的硬指标，以"同一台机器上比 WPS 快"为目标**。基准测试套件持续对比 WPS，结果写进发布说明 | 用户选定。为了能衡量，仍然保留基准测试和回归检测（只报警，不阻塞合并） | 2026-11-14 | Accepted |
| D-013 | 方案形态：**既给人看，也给 AI Agent 长时间自主执行**。里程碑拆成带验收标准和验证命令的任务；仓库里放 `AGENTS.md` | 用户选定 | 2026-11-14 | Accepted |
| D-014 | 套件扩展顺序：**表格 1.0 → 文字处理 → 演示**；三者共用一个应用外壳（一体化窗口，标签页打开不同类型的文件） | 文字处理能复用表格阶段的富文本、渲染抽象和应用框架；演示对矢量绘图要求最高，放最后 | 2026-11-14 | Accepted |
| D-015 | 语言：**简体中文 + 英文从第一天起就支持**，界面文字一律走 i18n，不允许硬编码；公式函数名保持英文 | 和 Excel/WPS 中文版的习惯一致 | 2026-11-14 | Accepted |
| D-016 | 工程：GitHub 托管 + GitHub Actions（macOS/Windows）；GitHub Releases 发布 .dmg/.msi；内置自动更新；正式版前做 Apple 签名和公证，Windows 代码签名稍后再上；Homebrew 和 winget 渠道 | 用户选定 | 2026-11-14 | Accepted |
| D-017 | **兼容性分级**：P0 打开不丢数据、公式结果一致、保存不破坏；P1 常用格式、图表、条件格式显示一致；P2 透视表等高级功能；P3 宏和 VBA 只保留不执行。用真实文件语料库加自动对比来衡量。**表格 1.0 的门槛是 P0 + P1** | 一个人的精力有限，必须分级 | 2026-11-14 | Accepted |

## 技术

| 编号 | 决策 | 理由 | 日期 | 状态 |
|---|---|---|---|---|
| T-001 | UI 框架：**GPUI + GPUI Kit**（`gpui-kit` 一个 crate 统一锁定 GPUI 快照版本） | 原生 GPU 渲染，性能和质感最好；GPUI Kit 有生产环境的验证（Longbridge Pro） | 2026-11-14 | Accepted |
| T-002 | **分层隔离**：模型、引擎、文件格式、排版、渲染抽象这几层**禁止依赖 `gpui`**；只有 `ordia-app`、`ordia-ui`、`*-view` 和 `ordia-render-gpui` 可以依赖 | 把 GPUI 的 API 变动限制在最上层；PDF 导出和屏幕显示能共用同一份绘制指令 | 2026-11-14 | Accepted |
| T-003 | 渲染抽象：所有文档内容先生成一份**与平台无关的绘制指令列表（DisplayList）**，再由 GPUI、PDF 等后端各自绘制 | 保证屏幕显示和 PDF 一致；以后可以加 vello 或 tiny-skia 后端 | 2026-11-14 | Accepted |
| T-004 | 依赖版本统一锁定：提交 `Cargo.lock`；用 `rust-toolchain.toml` 固定 Rust 版本；GPUI Kit 升级必须作为单独任务，集中处理 | GPUI 的 API 还不稳定 | 2026-11-14 | Accepted |
| T-005 | **默认不收集任何遥测数据**；崩溃报告由用户主动选择是否上传 | 开源社区对隐私的预期 | 2026-11-14 | Accepted |
